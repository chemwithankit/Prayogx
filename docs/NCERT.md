# NCERT Explorer

A second content track beside the JEE Questions Library: a student reads the official NCERT chapter
and, beside it, explores the PrayogX simulations that make the section they are reading visible.
Approved by the owner on 2026-10-02 (decisions in [DECISIONS.md](DECISIONS.md)).

```
PRAYOGX
├── JEE QUESTIONS LIBRARY      APPLY   question → simulation           (index.html, content/index.json)
├── NCERT EXPLORER             LEARN   NCERT concept → simulation      (/ncert/, content/ncert/)
├── shared simulation engine   one self-contained index.html per page, the same G5 standard
├── shared media pipeline      tools/reel-maker (docs/NCERT_MEDIA.md)
└── shared publishing pipeline publish.sh, instagram_publish.py, youtube_publish.py, the ledger
```

The two libraries are **separate discovery systems over one simulation library**. The NCERT layer
never edits a simulation record: it links to pages by ID.

---

## 1. Principles

- **Additive.** Nothing in the JEE library changes to make room for NCERT. The JEE feed, its
  crawlable pages, the sitemap and the service-worker stamp stay byte-identical when NCERT content
  is added (`tests/ncert_data.py` checks this).
- **NCERT stays the primary text.** PrayogX does not host, proxy or redistribute NCERT PDFs (§4).
- **The owner chooses every concept.** A chapter is studied first and candidates are proposed; only
  approved concepts are built.
- **Scientific correctness outranks visual effects**, exactly as in the JEE library.
- **The strongest representation, not always a simulation** (§2).

## 2. Choosing the representation (owner's visual learning objective, 2026-10-02)

Every important concept should be visually understandable and experimentally explorable. Before a
concept page is designed, its blueprint picks the representation that teaches it best, in this order:

| Representation | Use it when |
|---|---|
| Interactive simulation | meaningful interaction is possible |
| Experimental / graph explorer | changing variables and observing data lets the student discover the relationship |
| Real-world simulation | a practical context makes the concept clearer |
| Animation (process, instrument, microscopic view) | the process is mainly visual, or cannot be meaningfully interacted with |
| Static visual explanation | only when interaction or animation adds no educational value |

Forms include virtual experiments with working instruments (show what happens *inside* the
instrument and why it reads what it reads), concept simulations, real-world simulations, graph
explorers, data exploration, and process animations of mechanisms, molecules, energy, forces and
fields.

The student's path: **see it → interact → manipulate → observe what changes → discover the
relationship → understand why → connect it to the theory → apply it to questions.** If a concept can
be seen, let the student see it; if it can be manipulated, let them manipulate it; if it can be
discovered, let them discover it; if it cannot be simulated meaningfully, explain it through a
powerful animation.

Every interaction must earn its place pedagogically: no interaction for visual novelty.

## 3. Data

### IDs

| What | Pattern | Example |
|---|---|---|
| Book | `NCERT-<CLASS>-<SUBJ>-P<n>` | `NCERT-11-CHE-P1` |
| Chapter | `<book>-CH<NN>` | `NCERT-11-CHE-P1-CH05` |
| Section | `intro`, `summary`, `exercises`, or the NCERT number | `5.1.4`, `5.4e` |
| Simulation | the existing `CON-<SUBJ>-<SLUG>` concept IDs | `CON-CHE-HESS-LAW` |

There are no separate NCERT simulation IDs. A concept page is a normal concept entry
(`tools/registry_schema.py`); its NCERT location is a mapping, not part of its identity.

### Files

```
data/ncert/catalog.json                    class → subject → book → chapter; official source; editions
data/ncert/chapters/<chapter-id>.json      sections, printed page ranges, the mapping
content/ncert/catalog.json                 GENERATED by tools/build_content.py
content/ncert/<chapter-id>.json            GENERATED: sections + cards of every linked simulation
```

Rules and the feed are in `tools/ncert_schema.py`; `tools/check_library.py` enforces them and fails
on a stale `content/ncert/`. Write the data files with Python `json`.

### A chapter

`catalog.json` holds, per chapter: `id`, `number`, `title`, `file`, and `source`:

| Field | Meaning |
|---|---|
| `official` | the NCERT download (`https://ncert.nic.in/textbook/pdf/<file>.pdf`) |
| `hosted` | **must be `null`**. It may be set only after written permission is recorded in DECISIONS.md. |
| `bookPages` | first and last printed page |
| `titleToken` | a word on the first page, used to recognise another reprint of the chapter |
| `editions` | fingerprinted PDFs: `label`, `sha256`, `pdfPages`, `pageLabels` (`book` = the PDF's page labels are the printed pages), `verified` date |

Each section has `id`, `number`, `title`, `level` (1 or 2), `pages` (printed, inclusive; sections may
share a boundary page), `concepts`, and the mapping:

| List | Holds | Shown as |
|---|---|---|
| `understand` | CON- concept simulations | UNDERSTAND |
| `watch` | `{"sim": <CON- id>, "asset": "animation" \| "reel"}` | WATCH, only once a VERIFIED record exists in `tools/reel-maker/publications.json` |
| `apply` | ADV- JEE simulations | APPLY: related JEE problems |
| `planned` | approved CON- pages not built yet | nothing; validated for form only |

A draft simulation linked in a section is left out of the feed until it is published.

### Publishing a concept

Concepts are shown **only** by the NCERT Explorer. `build_content.py` keeps them out of the JEE feed,
the crawlable `s/` pages and the sitemap; the revision lock covers them, because they are cached by
revision like every page. A concept may be published (`script_verified`, or `human_verified` after
the owner's review) only when `registry_schema.CONCEPT_PUBLISHABLE` is on **and** a chapter maps it
under `understand`. The flag is switched on in Phase 5, when the NCERT page can open a concept.

## 4. The PDF source

NCERT chapter PDFs carry "not to be republished", are served with `X-Frame-Options: SAMEORIGIN` and
no CORS header, and the Pages deploy refuses any PDF. So:

1. **Local file (primary).** The student downloads the official chapter, then opens it in PrayogX.
   PDF.js reads it in the browser; a copy is kept on the device (IndexedDB) so the next visit opens
   straight to the last page. Nothing is uploaded anywhere.
2. **Official link (fallback).** "Read Official NCERT PDF ↗" opens the NCERT file in a new tab. The
   dashboard still works, driven by the section list and an "I'm on page …" box.
3. **Hosted.** Disabled (`hosted: null`). The source layer is an adapter, so official hosting can be
   added later without redesigning the reader, once permission is recorded.

A file is matched by its SHA-256 against `editions` (exact page sync). Otherwise, if its page labels
fall in `bookPages` and the first page contains `titleToken`, it is treated as another reprint
(section mapping kept, page links marked approximate). Anything else is refused for this chapter.

Measured on 2026-10-02 with a scratch prototype (PDF.js 6.3.289, the real `kech105.pdf`):
desktop Chromium and Android-emulated Chromium open it in about 1.2 s, render, search its text,
read page labels 136–167, restore it from IndexedDB after a reload with the same hash, and refuse a
broken PDF cleanly, with no console errors. iOS Safari could not be tested on the build machine; the
real-device checklist (iPhone and Android phone, browser and home-screen app) is the exit gate of
Phase 3. If local files prove unreliable on a platform, that platform defaults to the official link.

PDF.js is vendored at a pinned version inside `/ncert/` only. The JEE site never loads it.

## 5. The page (Phases 2–5)

`/ncert/` is its own page; the JEE `index.html` and `site/site.js` are not changed, apart from one
header link added at the final approval gate. Until then the page is unlinked and `noindex`.

- Desktop / tablet: a dashboard (about 30 %) beside the reader. The dashboard shows the chapter,
  progress, **On this page** (UNDERSTAND / WATCH / APPLY for the section being read), the chapter map
  and bookmarks. The reader has page controls, zoom and fit modes, search, thumbnails, night mode and
  full screen.
- Mobile: the reader fills the screen; the dashboard is a bottom sheet.
- A simulation opens in an overlay above the reader, which stays mounted: "‹ Back to p. 151" returns
  to the same page and zoom. APPLY pages also offer "Open in JEE library ↗".
- Progress is client-side only (`localStorage` `prayogx-ncert:v1`, the PDF in IndexedDB
  `prayogx-ncert`): page, section, opened simulations, the student's "Done". No accounts, no backend.
